# 独立系统验收

一个系统对应一份开发交付和一份独立验收报告。开发 agent 负责实现与自测；另一个 agent 负责验收与复验。验收通过只适用于记录的交付版本、产品需求和检查范围，不代表整个产品或所有系统已通过。本技能定义工作方式，不自动派发 agent；仅整理技能时不要启动真实项目验收。

必读 [开发规范](../development-rules/SKILL.md)、目标系统 SKILL，以及 [CLI 验收说明](../../../integrations/codex/cli/README.md)。涉及 Widget 时读 [Widget](../widget/SKILL.md) 和 [Widget Extension](../widget-extension/SKILL.md)；实际操作 Unity 时按可用的 unity-cli 技能执行。缺少必要工具时如实记录未完成项，不假装执行。

## 独立性与边界

- 验收 agent 不负责本轮被验收代码的编写或修复。开发自测结果是线索，不能替代独立执行与取证。
- 从产品需求、指定设计版本、真实文件和工具结果得出结论，不依赖开发 agent 的“已完成”描述。报告每个问题的依据、复现步骤与证据位置。
- 不修改业务源码、预制、绑定、数据库模板、基准设计或验收规则来让结果通过。修复交回开发 agent；工具缺陷单独登记，不能当作业务缺陷或静默忽略。
- 可以编译、导出和进行任务范围内可逆的运行测试；证据和临时测试材料写入单独目录，不进入产品源码。真实登录、网络写入、存档清除等副作用须遵守产品任务授权，不能以验收名义扩大权限。
- 对同一 Unity 工程串行操作 Editor。开发修改、资源生成和验收不能同时发生；跨系统共享文件由集成负责人协调。多个验收 agent 可以检查各自文件，但不能争用同一编辑器或改动同一交付版本。

## 输入与交付冻结

先从任务和工程收集以下内容，只有无法查明的必要项才询问：

1. 产品需求及已确认设计变更；本轮系统、功能范围、明确不包含的功能。
2. Studio projectId、已验证的 Unity 工程身份，目标系统 SKILL。
3. 标准模板 ID/版本、产品设计 revision、每个页面的项目根节点 prefabId 和实际 prefab 路径。数据库标准模板 ID 不能代替 prefabId。
4. 开发交付版本：提交号（若已有）、未提交修改清单、源码/资源路径及内容哈希。提交不是验收前提，但必须能标识被测内容。
5. 对外接口、依赖版本、配置入口、测试数据与可复现的启动/关闭步骤；开发自测和已知待接接口。

Studio 项目先按仓库 AGENTS.md 检查 projectId 的绑定及 `ProjectSettings/GameCLIProject.json`，只使用返回的工程路径，不默认使用 development 或 practice。独立指定的非 Studio 工程不伪造项目 ID；当前命令需要绑定时记录工具适用限制。

以已确认产品需求和设计为验收基准。标准模板提供范式，用户未要求变更的设计沿用所选版本；已确认的产品改动不因与原模板不同而判失败。发现产品设计未保存或设计变更没有明确结论时，不擅自修改基准，相关项记为未完成。

记录开始和结束时的版本/哈希。验收期间交付发生变化时，受影响证据失效，重新冻结并复验；不要把不同版本的通过项拼成一份通过报告。

## 执行顺序

### 1. 代码与编译

在 GameCLI 的 `integrations/codex` 下运行（Windows 使用 pwsh.exe）：

```powershell
.\gamecli.cmd verify code --project <项目ID> --system <实际系统目录名>
```

该命令只扫描 `Assets/Scripts/Systems/<目录名>`。对交付的其他路径（例如 Launch 组件和 XApp 集成）另外按共享规范审查并列出实际覆盖文件，禁止为了适配命令搬动代码，或把未扫描内容描述为自动通过。

保存原始 JSON 与退出码。代码 `reviewRequired`、注释含义、功能分块、Entity/VM 职责、空值处理、异步与生命周期仍需独立审查。注释率和空行率只作统计，不自行设置百分比门槛。随后对正确 Unity 工程执行编译并检查 Console；静态语法通过不代表 Unity 编译成功。

### 2. 预制与静态绑定

对本次所有适用页面与列表项分别执行：

```powershell
.\gamecli.cmd verify prefab --project <项目ID> --prefab <项目根节点ID> --asset Assets/Data/Widgets/<模块>/<页面>.prefab
```

没有独立项目根节点的子预制不能冒充根节点调用。记录覆盖缺口并用适用的独立检查补证；不能只验主页面就声称子页面和列表项通过。Master 等纯代码系统的预制检查为“不适用”，附上需求依据；不创建 UI 来满足检查。

分别读取整体 `status`、`differences`、`unverified` 和 `bindings`。绑定子项通过不能替代整体通过。当前静态绑定检查包含类型、字段覆盖/顺序、Sync、生成属性、组件引用与重复项；Widget 可由 UISystem 在运行时添加，不能要求它必须序列化在页面根上。

当前导出证据不覆盖全部动画、资源身份和自定义组件，也不证明某个合法组件就是产品指定的绑定目标。按 CLI 说明逐项辨认缺口。缺少导出适配器时请求环境负责人补齐工具并重新编译，验收命令不能自行安装工具或放宽规则。

### 3. 运行行为与产品需求

从产品需求逐项生成可复现用例，至少覆盖本轮适用的入口、显示/数据刷新、交互、关闭/卸载、重开以及要求的失败分支。不扩展未授权业务，不把占位行为当成真实服务成功。

UI 模块实际观察 VM 更新是否作用到指定控件、按钮是否触发正确行为、关闭后监听是否释放、再次打开是否重复回调。验证实际可见的动画和点击遮挡；静态绑定通过不能替代这些结果。纯代码模块检查输入事件、状态与输出事件，不要求截图证明代码行为。

运行取证记录步骤、输入、预期、实际和日志/截图/状态证据；截图不能单独证明 VM 更新或回调次数。无接口、无测试数据或 Editor 不可用时明确标为未完成，不编造模拟成功。临时测试完成后清理临时实例并记录编辑器状态变化，不保存测试修改到产品资源。

## 判定与复验

每个检查项只使用：`passed`、`failed`、`incomplete`、`not-applicable`。失败代表已确认不满足需求；未完成代表证据、环境或契约不足；不适用必须说明依据，不能用来隐藏工具不支持的必需检查。

- 总体 `failed`：存在至少一项已确认缺陷；同时列出仍未完成的检查。
- 总体 `incomplete`：尚无已确认缺陷，但存在必需检查缺口。
- 总体 `passed`：所有适用的必需项均有本版本的充分证据通过，无未解决缺陷或缺口。

CLI 原始状态和退出码原样保留。工具显示 incomplete 时不得改写为 passed；可以另外提供独立补充证据，逐项对应 unverified 并说明证明范围，只有缺口确实闭合才能在综合报告中判该项通过。无法独立证明的项继续 incomplete。不得通过删除组件、忽略诊断或降低规则来闭合缺口。

失败后输出问题清单交回开发 agent，不直接修复。开发提供新的交付版本后，复验修复项及其受影响的绑定、生命周期和依赖；保留原报告与新报告的关联。无证据失效的其他范围不机械重复全量测试。

## 必须交付的报告

报告保存在明确的验收产物目录，例如目标工程 `Library/GameCLI/Acceptance/<系统>/<run-id>/`，不要将 Library 内证据误当永久存档；需要长期保存时由负责人复制到指定交付目录。

报告应包含：

- 系统、验收 agent、时间、工程身份、模板/产品设计版本、被测提交与文件哈希、范围和不包含项。
- 每条需求对应的用例、结果、证据路径；代码/预制原始 JSON、退出码、编译与 Console 结果。
- 自动检查、独立代码审查、运行检查分别覆盖了什么；补证与原始 unverified 的对应关系。
- 问题编号、定位（文件行号或节点/字段）、复现步骤、预期/实际、影响与建议处理者。
- 总体结论、未完成项、不适用依据、复验关联及仍需集成负责人检查的跨系统流程。

验收不自动提交推送、发布数据库模板或批准上线。每个系统独立通过后，集成负责人仍需检查跨系统接口和共享资源；系统验收报告不能冒充产品端到端验收报告。
